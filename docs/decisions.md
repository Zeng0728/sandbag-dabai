# 设计决策记录

> 记录"为什么这么选"，避免以后反复讨论。每条都写：背景 → 选择 → 理由 → 代价。

## D1 前后端同仓（monorepo）

- **背景**：3~5 人小团队，前后端经常同时改一个需求。
- **选择**：单仓库 `frontend/` + `backend/`。
- **理由**：一次提交能同时体现前后端改动，评审时不用来回切两个仓库。
- **代价**：仓库稍大；CI 需要按目录分别构建。

## D2 大模型做 mock 降级

- **背景**：别人 clone 下来没有 API Key，不应该因此跑不起来。
- **选择**：`llm.py` 里先试真模型，失败或无 key 就返回规则生成的 mock 回复。
- **理由**：演示、断网、新同事上手都不受阻；`/api/health` 会明示当前模式。
- **代价**：mock 回复质量有限，容易让人误判产品体验。

## D3 两种人格（target / dabai）

- **背景**：需求里既要"上传的东西能被对话"，产品上又需要"大白陪你"。
- **选择**：`/api/chat` 加 `persona` 参数，同一接口两种人格。
- **理由**：复用同一套上下文与留痕逻辑，前端一个聊天气泡就够。
- **代价**：prompt 需要分别维护，测试要覆盖两条路径。

## D4 火气值替代血条

- **背景**："血条"这个词跟"陪伴/疗愈"的定位冲突。
- **选择**：UI 与接口统一叫 `hp`，但界面文案叫"火气值"，归零 = 消气。
- **理由**：打完是"消气"，不是"杀死"。
- **代价**：代码变量名和界面文案不一致，需在 README 说明。

## D5 击打数值（初版）

| 方式 | 伤害 | 设计意图 |
| --- | --- | --- |
| 拳套 glove | 3 | 高频低伤，鼓励连击 |
| 石块 rock | 10 | 中伤，需瞄准 |
| 重击 heavy | 28 | 一击破防，但有前摇 |

- **初始火气 28**：正好等于一次重击，让玩家第一下就看到明显反馈。
- **代价**：数值未做真人测试，后续必须验证。

## D6 限流用内存令牌桶

- **背景**：大模型调用要花钱，必须防刷。
- **选择**：每 IP 每分钟 20 次，进程内字典实现。
- **理由**：零依赖，MVP 够用。
- **代价**：多进程/多实例部署失效，需换 Redis。

## D7 上传大小限制 5MB、只收图片

- **理由**：手机直出照片通常 2~4MB；限制类型可避免上传 PDF/压缩包。
- **代价**：超大图会被拒，需要前端压缩（待做）。

## D8 不存用户原图到仓库

- **选择**：`backend/storage/uploads/*` 进 .gitignore，只保留 `.gitkeep`。
- **理由**：上传内容属于用户隐私，不该出现在代码仓库历史里。
